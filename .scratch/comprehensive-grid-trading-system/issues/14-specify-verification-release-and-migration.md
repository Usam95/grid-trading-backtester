## Answer

Use the accepted [verification, release, and migration specification](../../../analysis/verification-release-and-migration-spec.md), grounded in the [code-gap audit](../../../analysis/verification-release-migration-code-gap-audit.md). The canonical projects evolve through characterized tested slices under three risk-based verification levels, owner-local suites, shared deterministic conformance scenarios, explicit parity fingerprints, strict critical-path quality/coverage/architecture gates, and a non-regressing legacy ratchet.

One locked Python workspace and frontend graph, pinned toolchain, clean source identity, immutable manifest, dependency inventory, and archive SHA-256 bind each result to exact bytes. Durable formats evolve through frozen forward-only expand–migrate–contract changes, immutable historical evidence, versioned readers/upcasters, verified recovery points, compatibility matrices, and no assumed destructive down-migration.

The local runner builds one offline target-compatible bundle; SSH stages it; Azure installs it side-by-side and verifies it frozen. Qualification, installation acceptance, and trading resume/activation are distinct authorities. Rollback is compatibility-driven, preserves failed evidence, never blindly replays commands, and uses reconciliation or forward recovery where state/external effects make an old binary unsafe. Minimal executable seam proofs protect later strategies/venues/sizing/multi-run/persistence/deployment evolution without implementing them. The exact three-process MVP must finally pass the accepted 24-hour B1ms capacity campaign, hard safety/deadline/evidence/RPO/RTO gates, and mandatory resize/retest when capacity fails.
