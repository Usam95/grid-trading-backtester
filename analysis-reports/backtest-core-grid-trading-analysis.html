1Executive summary

A well-structured, genuinely-engineered grid-trading research core — held back by an optimistic fill model, a feature-thin "fast" engine, and the absence of overfitting controls.

6.2/10
Overall engineering quality: solid (6–7/10). Clean architecture, real performance work, good unit coverage. Decision-grade backtesting readiness: not yet. The engine is an excellent internal research tool for single-symbol spot long grids, but it is not safe to present as a paid, trustworthy backtest product without fixing fill realism, stop accounting, fast/full parity, and adding walk-forward / robustness validation.

Three issues verified by running the engine
  1. Trade ledger ≠ equity. With bootstrap inventory, sum(trade.net_pnl)=4.6010 but equity change =4.5000 — bootstrap lots are never registered with the trade builder.
  2. Default static grid isn't two-sided. Under long_only bootstrap, both initial SELL rungs are silently rejected (no base to sell); a 5-level grid seeded only ['BUY','BUY'].
  3. No fast/full parity tests. No test references FastBacktestEngine; the Numba dynamic kernel ignores most of DynamicGridConfig — sweeps can rank the wrong candidate.

Monetization verdict: a standalone "grid backtester" has a thin moat (free native exchange bots; mature open-source frameworks). The realistic path is a grid-specialised research & reporting product — and a grid-backtest-saas (FastAPI + workers + frontend) already exists in this repo, so productization is underway. Probability of a sustainable niche business: moderate (~25–35%), conditional on shipping trustworthy validation and a polished report.

2Codebase overview — what it does

grid_backtest is a pure-computation library: the engine performs no file or network I/O and has zero exchange knowledge — data is handed in as a pandas OHLCV DataFrame (design principles in README.md are actually honoured). It ships:

  • Two engines. BacktestEngine (engine.py) is the accurate per-candle Python loop; FastBacktestEngine (engine_fast.py + _numba_engine.py) is a Numba-JIT kernel (~200–400× faster) for the two built-in grids only.
  • Two strategies. SimpleGridStrategy (static spot grid, arithmetic/geometric spacing) and DynamicGridStrategy (ATR/percent adaptive range & spacing, SL/TP, RSI/EMA/ADX filters, floating-grid recentering) — composed from isolated policy objects.
  • Research layer. GridResearchRunner (multi-process parameter sweep across params × timeframes) and grid_search_fast.py (Numba single-core sweep).
  • Results layer. pluggable MetricRegistry (Sharpe/Sortino/Calmar/profit factor/ win rate/max DD), FIFO TradeBuilder, repository (JSON/CSV persistence), Buy&Hold benchmark.

3Architecture assessment

Strengths

  • True separation of concerns. I/O-free engine; exchange-agnostic; DataSource protocol inverts data loading.
  • Command pattern (EngineAction) with strict __post_init__ validation.
  • Policy composition — range/space/sltp/filter/recenter are independent and unit-testable; DynamicGrid wraps SimpleGrid.
  • Open/closed metrics via MetricRegistry.
  • Real performance work — Numba kernel, object.__new__ candle path, insertion-order FIFO, multi-process sweeps.

Weaknesses

  • Two engines, no shared core → every feature must be built twice or diverge.
  • Two FIFO ledgers (engine cash vs TradeBuilder) that can disagree.
  • Fast engine is feature-thin and hard-codes isinstance dispatch — custom strategies can't use it; dynamic kernel ignores ATR/SLTP/filters.
  • Vestigial state — AccountState.base_free/locked/quote_free/locked unused.
  • Undocumented config interactions (long-only seeding asymmetry).

What the literature and the live bot market say about when grids win, when they blow up, and how to evaluate them. Full citations in §10.

When grids work

  • Range-bound, choppy, mean-reverting markets.
  • Moderate volatility; tight spreads & low fees (grids are high-trade-count).
  • Adaptive spacing (ATR) + trend filter reduces blow-up risk.

When grids fail

  • Strong one-directional trends / breakouts → underwater inventory, deep drawdown.
  • Leverage + trend → forced liquidation (often ignored in naive backtests).
  • Fat-tail / black-swan moves; martingale sizing → risk of ruin despite high win rate.
Realistic profitability expectations (practitioner consensus, not guarantees)
Sustainable grid configs target roughly ~2–10%/month with >30% drawdown risk in adverse trends; advertised "20%+/month" implies high ruin risk. Most grids look great in-sample until a persistent trend appears. Evaluate with profit factor, Sharpe/Sortino/Calmar, max drawdown & duration, exposure/turnover, and — critically — out-of-sample performance.
Methodology cautions that apply directly to this engine
  • Intrabar fill optimism: assuming a limit order fills whenever a bar's high/low touches its price overstates fills (OHLC hides intrabar sequence) — exactly the engine's same-bar model.
  • Backtest overfitting / deflated Sharpe (Bailey & López de Prado): sweeping many parameters inflates the "best" result; correct with walk-forward + deflated Sharpe.
  • Leverage/liquidation must be modelled for any futures-grid claim to be honest.

Hidden assumptions

  • Columns must be exactly Open/High/Low/Close/Volume with a DatetimeIndex.
  • Single symbol per engine; no cross-symbol portfolio or correlation.
  • Spot, long-only inventory; no funding/borrow → futures grids unrepresentable despite advanced-sounding config.
  • One equity point per candle (memory + annualisation implications on long 1m series).

Where the design is clean vs where it blocks future grid work

Clean

  • I/O-free engine boundary & command pattern.
  • Policy composition for adaptive grids.
  • Metric registry & data protocol.
  • Real, measured performance optimisation.

Blocks future work

  • Fill model is the foundation and the weakest part — every metric inherits its optimism.
  • Two engines + two FIFO ledgers with no parity harness.
  • Fast path can't run custom strategies (isinstance dispatch).
  • No margin abstraction → futures/short is a large retrofit, not an add-on.
Test posture
103 unit tests give good coverage of the Python engine, execution policies, metrics, and trade builder. Gaps: no fast/full parity tests, hypothesis is a declared dev dep but never used (no property-based invariants like cash conservation / FIFO equivalence), and no test pins the trade-vs-equity reconciliation or the seeding asymmetry.

7Monetization assessment

Can this be sold? Yes, but not as "a grid bot." The defensible product is trustworthy grid research + presentable reports, ideally with adaptive-parameter guidance.

Context: productization is already underway
A sibling grid-backtest-saas/ exists in this repo (FastAPI backend with api/core/db/schemas/services/workers, alembic migrations, a frontend, and infra/docker), consuming this core. So the question is less "can it be productized" and more "is the core trustworthy enough to charge for."

Differentiation that could work

  • Honest validation (walk-forward, Monte Carlo, deflated Sharpe) — most retail tools don't.
  • Grid-specialised analytics: per-rung profitability, inventory/exposure-over-time, fee drag, time-in-drawdown.
  • Regime-aware parameter recommendation per asset/timeframe.
  • Beautiful, shareable reports — the thing people actually pay for.

Gaps before commercial launch

  • Fix fill realism, stop accounting, fast/full parity, metric definitions (trust).
  • Add walk-forward + robustness (defensibility).
  • Report renderer + benchmark suite (presentability).
  • Clear disclaimers; no performance guarantees (compliance).
Trust, legal & compliance
Anything implying trading advice or returns invites regulatory and reputational risk. Position as research/education software, not signals; ship explicit "past performance ≠ future results" disclaimers; never auto-trade real funds without separate, heavily-disclaimed infrastructure. The optimistic fill model is itself a liability if results are presented as decision-grade.
Realistic probability (not hype)
  • Grid trading alone is not enough to anchor a durable business — native bots are free and the moat is thin.
  • ~15% chance as a generic paid grid backtester (commoditised).
  • ~25–35% chance as a grid-specialised research & reporting niche product if the correctness + validation gaps are closed and reports are excellent.
  • Higher as an internal quant research tool / lead-gen for paid reports than as a standalone subscription.

8Enhancement roadmap (prioritised)

P0 — correctness & trust (before any paid report)

  • Conservative intrabar fill mode (fill from bar N+1; worst-case buy/sell ordering).
  • Forced exits at the SL/TP trigger price (not the bar close), with slippage & gap handling.
  • Reconcile trade ledger with equity (register bootstrap lots with TradeBuilder).
  • Fast/full parity tests; restrict the fast engine to the subset it truly models.
  • Maker/taker fees; fix Sharpe annualisation, intrabar drawdown, avg_trade_pnl, profit_factor.
  • Document (and offer a true-neutral alternative to) the long-only seeding asymmetry.

P1 — research completeness

  • Walk-forward runner; deflated Sharpe / PBO in sweep ranking; Monte Carlo robustness.
  • Inventory/exposure caps; spread + volume-aware partial fills; inventory-aware recentering.

P2 — new universes

  • Short lifecycle + neutral/short grid; margin + funding + liquidation; multi-symbol portfolio; DCA/martingale sizing with ruin guards.

P3 — product surface

  • HTML/PDF report renderer; regime tagging + adaptive-parameter recommendation; benchmark suite (DCA/50-50); property-based tests via the already-declared hypothesis.

Full table with effort estimates and file touch-points in roadmap.md.

9Top prioritised recommendations

  1. Make fills honest first. Add a conservative intrabar fill mode + fill the foundation once (partials, spread, maker/taker). Everything downstream inherits this.
  2. Fix stop accounting & reconcile the trade ledger to equity. These are correctness bugs, not modelling choices, and they're cheap to fix.
  3. Add walk-forward + Monte Carlo + deflated Sharpe. The literature's clearest message: without OOS validation, the "best" grid from a sweep is usually noise.
  4. Lock the two engines together with parity tests (and use the already-declared hypothesis for cash-conservation/FIFO invariants), or collapse to one shared kernel.
  5. Build the report renderer. A polished, defensible HTML/PDF report is the actual sellable artifact and the bridge to the existing SaaS.
Is it currently suitable for serious grid-trading backtesting?
No — not yet for decision-grade or leveraged work. It is a strong tool for exploratory, single-symbol spot long grid research. The same-bar fill optimism, stop-at-close accounting, fast/full divergence, and absence of overfitting controls mean results should be treated as indicative, not decision-grade, until P0+P1 land.
Recommended next implementation step
Ship the P0 "trust pass" as one focused branch: (1) forced-exit-at-trigger price, (2) trade-ledger/equity reconciliation, (3) fixed metric definitions + intrabar drawdown, (4) a documented conservative fill flag — each with a regression test. This removes the embarrassing/wrong behaviour with the least effort and unblocks credible reporting.
